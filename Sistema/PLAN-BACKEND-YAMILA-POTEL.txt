 2. ARQUITECTURA OBJETIVO
==============================================================

                    +----------------------+
   Visitante ------>|  WEB ESTÁTICA       |  (HTML/CSS/JS)
                    |  Hosting a definir   |
                    +----------+-----------+
                               |
             POST JSON (fetch) |  ?tipo=contacto | diagnostico
                               v
                    +----------------------+
                    |  GOOGLE APPS SCRIPT  |  <-- backend/API
                    |  (Web App desplegada)|
                    +--+--------+--------+-+
                       |        |        |
                       v        v        v
                  SHEETS     GMAIL     (verifica tokens
               (registro)  (respaldo)   para el admin)

   Panel de Yamila (admin.html, en la misma web):
     Yamila ingresa con su cuenta de Firebase Auth (única cuenta
     creada a mano, sin registro público) -> el front obtiene un
     ID token -> se lo manda a Apps Script -> Apps Script lo
     VERIFICA contra Firebase -> devuelve los datos -> dashboard.

Principios del diseño:
 - UN solo backend: Apps Script. No levantar servidor Node
   duplicado que termine siendo una segunda fuente de verdad.
 - UNA sola cuenta Google para todo (ya creada).
 - El hosting puede ser cualquier estático (GitHub Pages,
   Netlify, Vercel, Cloudflare Pages, o un VPS): el "backend"
   vive en Google. Si más adelante se quiere VPS con backend
   propio, la migración es cambiar el endpoint del fetch.
 - Nada de credenciales SMTP ni secretos reales en el frontend:
   todo lo sensible vive del lado de Apps Script.

3.1 GOOGLE APPS SCRIPT (el backend)
--------------------------------------------------------------------
Proyecto en script.google.com vinculado a la hoja de cálculo
"YP - Base de datos" (nombre a definir), desplegado como Web App.

Endpoints:
  doPost(e)  -> recibe JSON con { tipo: "contacto" | "diagnostico", ... }
                - valida forma del payload (campos obligatorios,
                  longitudes máximas, tipo de dato)
                - honeypot anti-spam (ver Fase 6)
                - agrega fila en la hoja correspondiente
                - le manda un email a Yamila (GmailApp, desde la
                  MISMA cuenta Gmail del proyecto)
                - responde { ok: true }
  doGet(e)   -> solo para el panel admin: exige header
                Authorization: Bearer <ID token de Firebase>,
                lo verifica contra Firebase (identitytoolkit
                accounts:lookup con la API key del proyecto) y
                devuelve los datos pedidos (resumen, lista,
                detalle). Nunca devuelve todo si no hay token
                válido.

Pasos de creación (checklist):
  [ ] Crear la hoja de cálculo en la cuenta nueva
  [ ] Extensiones -> Apps Script, vinculado a esa hoja
  [ ] Código: doPost + doGet + helpers (una función por tipo)
  [ ] Implementar como app web:
        - Ejecutar como: Yo
        - Quién tiene acceso: Cualquier persona con el enlace
      (el acceso "abierto" se compensa con validación de payload
       y con verificación de token en doGet; ver 7. Riesgos)
  [ ] Copiar la URL /exec  -> es el endpoint de la web
  [ ] Importante: cada cambio de código requiere volver a
      implementar (nueva versión) o usar un deploy de prueba

3.2 GOOGLE SHEETS (la base de datos / el "Google Docs" que pidió
    la clienta)
--------------------------------------------------------------------
Una hoja con dos pestañas. Ella la ve y la usa como registro.
No hace falta más base de datos por ahora.

  Pestaña "Consultas" (formulario de contacto):
    fecha | origen | servicio | nombre | email | telefono |
    campos_extra | mensaje | estado

    - fecha: ISO 2026-10-28T14:32:00 (fácil de ordenar/filtrar)
    - origen: "boton_servicios" | "home" | "directo"
    - servicio: clave corta (impositiva, costos, flujo,
      importaciones, diagnostico-inicial, otras-consultas)
    - campos_extra: los campos opcionales dinámicos concatenados
      como "situacion_fiscal: Monotributo | detalle_impositivo: ..."
      (alternativa si prefiere: una columna por campo; hay ~14
      campos distintos entre los 4 servicios)
    - estado: columna vacía con validación de datos (dropdown)
      para que Yamila marque: pendiente / contactado / propuesta
      enviada / cerrada

  Pestaña "Diagnosticos" (cuestionario de 6 pasos):
    fecha | estado | nombre | negocio | rubro | antiguedad |
    tipo_gestion | registro_movimientos | frecuencia_revision |
    sistema_registro | medios_cobro | pct_facturacion |
    nivel_facturacion | cuenta_bancaria | cuenta_exclusiva |
    retiros_personales | punto_equilibrio | fondo_reserva |
    control_costos | desafio_principal | comentarios

    (las columnas salen de FIELD_LABELS en diagnostico.js, ya
     mapeadas 1:1)

3.3 GMAIL (cuenta nueva del proyecto) — respaldo
--------------------------------------------------------------------
Apps Script envía el mail con GmailApp desde la propia cuenta.
Cada consulta genera:
  Asunto: [Web Yamila Potel] Nueva consulta - Asesoría impositiva
  Cuerpo: los mismos datos de la fila de la planilla
  -> si un día la planilla falla o se borra, el respaldo está
     en el inbox con etiqueta automática ([Web Yamila Potel])

Decisiones:
  - El mail es NOTIFICACIÓN + respaldo; el registro canónico es
    la planilla.
  - Cuota de Apps Script: ~100 emails/día en cuentas gratuitas
    (suficiente de sobra para el volumen de una consultora).

3.5 ADMIN.HTML (dashboard privado)
--------------------------------------------------------------------
Página en la misma web, sin link en el menú ni en el footer
(solo se llega escribiendo la URL).

  Login: email + contraseña de la cuenta única de Firebase.
  Una vez adentro:
    - Resumen: consultas de los últimos 30 días, por servicio,
      diagnósticos nuevos, pendientes.
    - Tabla de consultas con filtro por fecha/servicio/estado.
    - Tabla de diagnósticos con detalle expandible.
    - Cambiar estado (pendiente -> contactado ...) que escribe
      de vuelta en la planilla (doPost con token).
    - Exportar CSV.
  Técnicamente: firebase.auth().signInWithEmailAndPassword()
  -> user.getIdToken() -> fetch a doGet/doPost de Apps Script
  con el token en el header -> Apps Script verifica -> datos.

  NO se usa Firestore por ahora: la fuente de verdad es la
  planilla. Si algún día el dashboard necesita consultas
  complejas o tiempo real, se puede espejar la hoja a Firestore
  sin tocar el frontend del admin.


==============================================================
 4. FLUJOS DE DATOS (qué pasa en cada acción del usuario)
==============================================================

FLUJO A — Consulta desde el formulario de contacto
  DECIDIDO: el mensaje COMPLETO de la consulta va a WhatsApp
  (automático) y queda el respaldo en Gmail vía G.A.S.

  1. Visitante llega desde servicios.html?servicio=X o desde el
     home (anclado) y completa el form (campos extra opcionales).
  2. Submit -> fetch POST a Apps Script { tipo: "contacto", ... }
     -> fila en pestaña "Consultas" + email de respaldo a Yamila
        (asunto: [Web Yamila Potel] Nueva consulta - <servicio>).
  3. Con la respuesta OK del servidor -> se abre WhatsApp (wa.me)
     con el mensaje prolijo (ver 4.1) y se muestra la tarjeta de
     cierre en el lugar del formulario.
  4. Al volver de WhatsApp (o si no se abrió), la tarjeta de
     cierre queda visible.
  5. INTERIM (estado actual, sin G.A.S): el submit abre WhatsApp
     con ese mismo mensaje y muestra la tarjeta; el respaldo en
     Gmail se suma en la Fase 2. El código queda marcado como
     "interim" para no olvidarlo.
  6. Si falla el fetch: mensaje de error + botón de WhatsApp
     como salida alternativa.

FLUJO B — Cuestionario diagnóstico
  DECIDIDO: el diagnóstico se centra en la planilla de Drive
  (ahí está el registro); el WhatsApp es solo una NOTIFICACIÓN
  corta. La redirección es automática y al volver queda la
  tarjeta de cierre.

  1. Usuario completa los 6 pasos (ya funciona).
  2. Al final: fetch POST { tipo: "diagnostico", ... } -> fila
     en la pestaña "Diagnosticos" (destino principal: el Drive)
     y, con la respuesta OK, se abre WhatsApp con el mensaje
     corto de notificación (ver 4.1).
  3. Vuelta desde WhatsApp -> tarjeta de cierre que reemplaza al
     wizard: "Relevamiento enviado", botón para escribir/
     reenviar, link a servicios y opción de hacerlo de nuevo.
  4. Persistencia: localStorage guarda que ya envió (con fecha);
     si la persona vuelve a entrar al diagnóstico, ve la tarjeta
     en vez del paso 6, con botón "Hacer el cuestionario de nuevo".
  5. El borrador de respuestas se limpia SOLO si el envío fue OK
     (hoy se limpia siempre; corregir en la Fase 3).

  INTERIM (estado actual, sin G.A.S): no se puede afirmar que
  "la planilla se actualizó" porque todavía no se guarda nada.
  Por eso diagnostico.js lleva una flag MODO_NOTIFICACION:
    - false (hoy): manda el detalle COMPLETO de las respuestas,
      con el formato prolijo de la sección 4.1.
    - true (cuando entre G.A.S): manda solo la notificación
      corta con el link a la planilla.

FLUJO C — Yamila entra al panel
  1. Escribe /admin.html -> login con su cuenta Firebase.
  2. Token -> Apps Script verifica -> listado y resúmenes.
  3. Marca una consulta como "contactada" -> Apps Script
     actualiza la celda de estado en la planilla.

FLUJO D — Canal directo (ya funciona, se mantiene)
  WhatsApp wa.me/5491139053672 con mensaje pre-armado.
  Sirve como salida de emergencia si el backend está caído.

==============================================================
 7. NOTAS TÉCNICAS Y RIESGOS (ojo con esto)
==============================================================
 - CORS: para no tropezar con el preflight, el fetch del front
   se hace con Content-Type: text/plain y el JSON en el body;
   Apps Script lo recibe igual (e.postData.contents).
 - El deploy de Apps Script NO toma cambios hasta volver a
   implementar (o usar un deploy de prueba durante desarrollo).
 - El endpoint /exec es "público" por cómo funciona Apps Script:
   la protección es validar el payload + honeypot + que doGet
   exija token. No es una API con usuarios reales.
 - NUNCA poner credenciales de Gmail/SMTP en el JS del front.
   Delegar todo el envío a Apps Script (que corre con los
   permisos de la cuenta).
 - wa.me redirige la página: si se abre en el mismo submit,
   hacerlo DESPUÉS de que el fetch responda OK.
 - Firebase config (apiKey, etc.) es pública por diseño: no es
   un secreto. La seguridad está en las cuentas existentes +
   Authorized domains + verificación de token del lado servidor.
 - localStorage del diagnóstico: no limpiarlo si el envío falla
   (hoy se limpia siempre; corregir en Fase 3).
 - Datos personales: al empezar a guardar, sumar consentimiento
   y actualizar la política de privacidad.
